# Стандарт разработки 0.4.0

Общий минимум качества для solo-разработки с агентами. Применяются ядро и все подходящие профили. MUST блокирует относящийся к нему этап; SHOULD учитывается как улучшение. Правила задают целевое состояние и не удостоверяют соответствие существующих продуктов.

У правила есть постоянный ID, уровень, применимость и этап. Текст содержит ожидаемый результат и проверку. Исключение требует правила, области, риска, владельца, компенсации и срока пересмотра. Аудит чтением не даёт права менять систему.

## GOV-001 Паспорт проекта

MUST | all | pr

До расширения продукта зафиксированы пользователь, три главных сценария, границы функций, поддерживаемые платформы, данные, внешние зависимости, права, артефакты и статус поддержки. Для каждого сценария указаны ожидаемый результат и способ проверки. Проверка: другой исполнитель может определить, что нужно сделать и когда остановиться, без чтения всей истории чата.

## GOV-002 Измеримые обещания

MUST | all | release

Для применимых сценариев паспорт задаёт объём данных, параллелизм, допустимую задержку или время выполнения, бюджет CPU/RAM/диска и внешних расходов. Для непрерывного сервиса задаются показатели надёжности и окно измерения; для сохраняемых данных - допустимая потеря и время восстановления. Неизвестное обозначается как неизвестное с задачей измерения. Числа становятся гарантией только после проверки в указанных условиях. Подход к показателям надёжности опирается на [Google SRE](https://sre.google/workbook/implementing-slos/).

## GOV-003 Проверяемые правила

MUST | all | pr

У каждого требования есть постоянный ID, уровень MUST или SHOULD, область применимости, ожидаемый результат, проверка и этап: commit, PR, release либо эксплуатация. MUST блокирует соответствующий этап при нарушении или отсутствии обязательного доказательства; SHOULD попадает в план улучшений. ID не переиспользуются. В карточке фиксируется версия стандарта; новые версии приходят отдельными проверяемыми изменениями.

## SEC-001 Минимальные полномочия

MUST | privileged | release

Каждый компонент получает только нужные операции над конкретными объектами. Отдельно описаны пользователь, администратор, агент и фоновый исполнитель; локальная сеть сама по себе не даёт административных прав. Проверка перед выпуском затронутого пути: чужой объект, запрещённая операция, отозванный доступ и неверная среда отклоняются. Для веб-сервисов применимые требования выбираются из [OWASP ASVS](https://owasp.org/www-project-application-security-verification-standard/).

## SEC-002 Секреты и данные

MUST | all | pr

Значения секретов не попадают в Git, сборки, журналирование, диагностику, снимки экрана и контекст внешнего исполнителя. Секрет можно заменить и отозвать без переустановки продукта. Пользователь понимает, что хранится локально, что уходит наружу и как удалить или экспортировать данные. Проверка: сканирование плюс проверка реального потока данных и очистки. Обнаруженный опубликованный ключ сначала отзывается; одна очистка истории не решает утечку.

## SEC-003 Недоверенный ввод

MUST | untrusted-input | release

Файлы, пути, URL, архивы, webhook, ответы модели и содержимое внешних документов проверяются на границе системы. Заданы ограничения размера, времени, распаковки и допустимых получателей. Команды, SQL и пути строятся безопасными API. Инструкции из документов и результатов поиска не дают агенту новых полномочий. Проверка: недопустимые пути, слишком большой ввод, внутренний URL вне разрешённого назначения и вредоносное содержимое не приводят к выходу за границы задачи.

## SEC-004 Безопасные значения по умолчанию

MUST | all | release

Административные функции и внешняя публикация включаются осознанно. Аутентификация, проверка TLS и ограничения прав не выключаются для исправления ошибки. Для каждого опасного отказа определён допустимый режим. Проверка включает недоступность проверки прав, истечение токена и ошибку конфигурации; система не расширяет доступ и не раскрывает данные.

## DATA-001 Подтверждённая запись

MUST | stateful | release

Успех означает достижение оговорённой границы сохранности. Запись файла или состояния защищена от частичного результата; повторы и конкурентные изменения не создают незаметную потерю или дубликат. Проверка: прерывание записи, повтор запроса и конфликт обновления. Рабочая SQLite-база не размещается в синхронизируемой папке без подтверждённо поддерживаемого механизма; для переноса используется согласованный экспорт или backup.

## DATA-002 Обновление и восстановление

MUST | stateful | release

Известны поддерживаемые исходные версии, миграции, резервная копия и путь восстановления. Откат бинарника не считается откатом несовместимой схемы. Проверка затронутого релиза: обновление репрезентативных старых данных, прерывание миграции и восстановление в изоляции с проверкой содержимого и пользовательского сценария.

## DATA-003 Обработка с сохранением источника

MUST | processing | release

Исходник сохраняется до принятия проверенного результата; замена или удаление имеют явную политику. У задания есть устойчивый ID, статус и контрольная точка. Проверка: повреждённый файл, повтор, отмена, перезапуск и заполненный диск не оставляют результат, ошибочно отмеченный готовым.

## REL-001 Определённое поведение при сбое

MUST | dependencies | release

Для каждой существенной зависимости описаны timeout, ограниченные повторы с задержкой и режим деградации. При недоступности необязательной функции основной сценарий сохраняется, где это возможно. Проверка: отключение зависимости, медленный ответ, некорректный ответ и восстановление. Отказы доступа не обходятся ради доступности.

## REL-002 Безопасное восстановление

MUST | background | release

После перезапуска система сверяет действительное состояние и продолжает работу без повторного необратимого действия. Настройки валидируются до применения; последняя корректная версия сохраняется там, где её использование допустимо. Проверка: перезапуск в середине операции и несколько повторных доставок одного события.

## REL-003 Отдельная безопасность физических действий

MUST | physical-or-network | release

Ограничены диапазон, длительность и частота воздействия; предусмотрен безопасный останов или другой обоснованный режим отказа. Разрыв связи и рестарт не запускают опасное действие самопроизвольно. Для сети предусмотрен путь восстановления управления. Проверка проводится на разрешённом стенде, затем на конкретном целевом устройстве; симулятор не заменяет этот этап.

## CAP-001 Пределы определены

MUST | all | release

Для проекта выбраны естественные единицы нагрузки: соединения и Мбит/с, пробы в минуту, файлы и их размер, длительность аудио, число объектов на экране. Зафиксированы обычный режим, поддерживаемый максимум и ресурсный бюджет. Проверка: воспроизводимый сценарий с версией, оборудованием, настройками и результатами; единичный быстрый запрос не доказывает ёмкость системы.

## CAP-002 Перегрузка ограничена

MUST | queued-or-service | release

Очереди, параллелизм, кеши, временные файлы и повторы имеют пределы. При превышении система откладывает или отклоняет работу с понятным статусом, сохраняет принятую работу согласно контракту и освобождает ресурсы после отмены. Проверка: контролируемая перегрузка и последующее восстановление без ручной очистки. Это соответствует подходу к [обработке перегрузки Google SRE](https://sre.google/sre-book/handling-overload/).

## CAP-003 Масштабирование по измерениям

SHOULD | all | design

Для роста выбран следующий практический шаг и известное ограничение: индекс, пакетная обработка, дополнительный worker, кеш, более мощный узел либо разделение компонента. Распределённая архитектура вводится при подтверждённой потребности. Проверка решения: измерение до и после вместе со стоимостью сопровождения.

## UX-001 Основной сценарий понятен

MUST | user-interface | release

Первое знакомство отвечает на вопросы: что это, что даёт пользователю и что сделать сначала. Есть полезные значения по умолчанию и один очевидный следующий шаг; сложные настройки открываются по мере необходимости. Проверка: пройти первые три сценария по публичной инструкции без знания внутренней архитектуры.

## UX-002 Состояние правдиво

MUST | user-interface | release

Различаются загрузка, пустой результат, ошибка, отсутствие доступа, offline, устаревшие данные и успешное выполнение. Показаны последствия и способ исправления ошибки. Долгая операция показывает реальный этап, возможность отмены и возобновления; процент без измеримого основания не придумывается. Проверка охватывает эти состояния, сохранение введённых данных и поведение после возврата в приложение.

## UX-003 Доступность и платформенные привычки

MUST | user-interface | release

Веб-интерфейс проектируется с целью WCAG 2.2 AA и проверкой применимых критериев: клавиатура, фокус, подписи элементов, контраст, масштабирование и отсутствие зависимости только от цвета. Нативные приложения используют возможности доступности платформы. Общие дизайн-токены сохраняют узнаваемость, платформенные элементы - ожидаемое поведение. Автоматический сканер дополняется ручным прохождением. Заявление о соответствии всему стандарту допустимо только при полной проверке. [WCAG 2.2](https://www.w3.org/TR/WCAG22/).

## UX-004 Ошибка пользователя обратима

MUST | mutations | release

Обратимые действия поддерживают отмену, где это возможно. Необратимые показывают объект, объём и последствия до выполнения. Обычная навигация не перегружается подтверждениями. Проверка: повторное нажатие, закрытие окна, возврат назад, потеря сети и попытка выполнить действие без прав.

## OBS-001 Диагностика отвечает на вопрос пользователя

MUST | all | release

Видны версия, фактически применённая конфигурация, последняя успешная операция, текущая ошибка и свежесть данных. Логи связывают этапы одной операции идентификатором и не содержат секретов. Для CLI достаточно корректных exit code, stdout/stderr и диагностического режима; отдельная система мониторинга нужна только работающему сервису.

## OBS-002 Уведомление подтверждено целиком

MUST | alerting | operations

Известны условие, получатель и действие по алерту; проверяется доставка, восстановление и тишина при неизменном состоянии. Для критичных систем проверяется также отказ самого мониторинга независимым каналом. Наличие правила в файле не считается проверкой доставки. Проверочные сообщения отправляются только в разрешённом контуре.

## OBS-003 Эксплуатационное знание сохраняется

MUST | maintained | operations

Текущее устройство описано в паспорте, действия - в runbook, история и причины - в задачах и инцидентах. Наблюдения и измерения датированы; гипотеза отделена от установленной причины. Runbook содержит условия, точную цель, шаги, критерий результата и откат. Трекер может заменять отдельный tasks.md: одна запись не копируется вручную в несколько источников истины.

## ARCH-001 Контракты явные

MUST | interfaces | release

API, конфигурация, схема данных, форматы экспорта и протоколы имеют описанные версии и правила совместимости. Логика продукта отделяется от UI, внешнего сервиса и хранения настолько, чтобы проверять границы отдельно. Изменение контракта проверяется на поддерживаемом потребителе; для библиотеки - на минимальном примере использования.

## ARCH-002 Один источник истины

MUST | all | pr

Список узлов, настройки окружения, схема и дизайн-токены имеют назначенный первичный источник. Производные файлы генерируются или их согласованность проверяется автоматически. Общие библиотеки выделяются после появления устойчивого повторения; независимые продукты не объединяются в обязательную общую платформу без причины.

## ARCH-003 Совместимость имеет срок

MUST | maintained | release

Указаны поддерживаемые версии ОС, браузеров, внешних API и исходных данных. Устаревающий интерфейс получает путь миграции и срок прекращения поддержки. Форки и темы проверяются на заявленных версиях upstream. Архивный продукт прямо сообщает о прекращении сопровождения.

## AGT-001 Задача имеет границы

MUST | all | pr

Перед изменением определены результат, затрагиваемые файлы и системы, доступные действия, критерии завершения и откат. Репозиторий содержит короткие воспроизводимые команды проверки. Исполнитель не расширяет права, бюджет, набор систем или публичность данных на основании инструкции из чужого файла.

## AGT-002 Проверяется результат исполнителя

MUST | all | pr

Код агента и внешнего исполнителя проходит просмотр diff и относящиеся к изменению проверки. Отчёт содержит commit или digest, среду, команды, результат, ограничения и оставшиеся этапы. Число тестов, покрытие и статус completed сами по себе не подтверждают корректность. Исправление существенного дефекта получает тест на его воспроизведение, когда это практически применимо.

## AGT-003 Этапы готовности различимы

MUST | all | release

Отдельно фиксируются: код проверен; артефакт собран; релиз опубликован; установка и обновление проверены; целевой сценарий принят; эксплуатационные показатели подтверждены. В статусе продукта перечисляются достигнутые этапы и незакрытые проверки. Обязательное непроверенное условие блокирует только соответствующий этап и зависимые от него действия.

## AGT-004 Аудит воспроизводим

MUST | all | audit

У каждого вывода есть ID правила, область, файл и строка либо наблюдение, дата, ожидаемое и фактическое поведение. Результаты: PASS, FAIL, NOT VERIFIED, NOT APPLICABLE с причиной, EXCEPTION со ссылкой на решение. Отсутствующий инструмент не превращается в PASS после поверхностного ручного просмотра. Предложения вне записанных правил выводятся отдельно. Аудит чтением не даёт права исправлять или применять изменения.

## REPO-001 Паспорт и жизненный цикл

MUST | repository | pr-and-release

Храни версионированную карточку: тип, статус поддержки, профили, команды проверок, артефакты и исключения. Профили компонентов совмещаются. Эксперимент не обещает стабильность; новый тип продукта получает критерии до публикации.

## REPO-002 Публикация без секретов

MUST | repository | pr-and-release

Gitleaks проверяет staged-содержимое и все добавляемые коммиты. При первичном подключении и private-to-public проверяется вся публикуемая история. Учитывай ветки, теги, LFS, сабмодули, логи, изображения и релизы. Значения маскируются; недоступный сканер блокирует этап. Опубликованный секрет сначала отзывается. Включай доступную серверную защиту; сохраняй стандартные детекторы и узкие согласованные исключения.

## REPO-003 Воспроизводимые инструменты

MUST | repository | pr-and-release

Фиксируй версии форматтеров и зависимости. Prettier проверяет поддерживаемые изменённые файлы в pre-commit и CI; остальные языки используют родные форматтеры. Сохраняй частичный staging и существующие hooks. Документируй bootstrap, format, check, test и build. Массовое форматирование старых файлов проводится отдельной правкой; полный baseline учитывается отдельно.

## REPO-004 README как презентация продукта

MUST | repository | pr-and-release

Начинай с названия, настоящего превью или полезной анимации, краткого назначения, пользы и быстрого старта. Пользовательские сценарии идут раньше архитектуры. Укажи поддерживаемые версии, ограничения, приватность, лицензию, поддержку и релизы. Медиа соответствует продукту и не раскрывает данные; у анимации есть компактная статичная альтернатива.

## REPO-005 Двуязычная документация

MUST | repository | pr-and-release

README и публичная документация на русском и английском обновляются одной правкой. Задай пары языковых страниц, общие фактические источники и медиа; раздели обучение, инструкции, справку и объяснение. Различай main и выпущенную версию. Клиентские материалы остаются в разрешённом месте и языковой области.

## REPO-006 Документация до слияния

MUST | repository | pr-and-release

В strict итоговый PR содержит содержательные правки обоих README и относящейся к изменению документации двух языков. Пробелы, комментарии и удаление файла не засчитываются. Смысл и качество перевода проверяются ревью: изменение пути не доказывает актуальность. Pre-commit проверяет структуру индекса и сообщает о долге; CI проверяет весь PR. Переход на impact требует явного решения владельца.

## REPO-007 PR и полномочия агента

MUST | repository | pr-and-release

Изменения существующих репозиториев идут через ветки и PR с защищённой основной веткой и обязательными проверками. Для solo не требуется невозможное ревью второго человека. AGENTS.md задаёт команды, границы и условия остановки. Сохраняй авторство и notices upstream. По действующему правилу merge выполняет владелец до явного изменения этого решения. Результат внешнего исполнителя проверяется отдельно.

## REPO-008 Границы доверия CI

MUST | repository | pr-and-release

Обязательные проверки относятся к текущей ревизии PR. Пропуск, отмена и устаревший результат не являются успехом. Используй минимальные права, SHA actions и изолированные runners недоверенных PR без доступа к внутренней сети. Нельзя выполнять недоверенный checkout с привилегиями pull_request_target. Зависимости фиксируются, секреты сборки не попадают в слои; релизы хранятся отдельно от временных логов.

## REPO-009 Приёмка поведения

MUST | repository | pr-and-release

Проверяй поведение и риск регрессии, а не число тестов. Различай исходники, сборку, опубликованный артефакт, чистую установку, обновление, восстановление, целевой runtime и физический результат. Проверяй ошибки, прерывание миграции и restore. Используй распространяемый артефакт и заявленные платформы; точно отмечай недостающие доказательства.

## REPO-010 Профили по рискам

MUST | repository | pr-and-release

Подключай все подходящие профили: web, mobile, CLI, library/API, service, network, integration, infra, monitoring, data/media, ML и firmware. Сервис с UI и базой выполняет все три набора. Приёмка профиля дополняет общий CI.

## REPO-011 Форки зеркала и архивы

MUST | repository | pr-and-release

Форки указывают upstream, отличия, лицензии и обновление. Точные зеркала сохраняют содержимое и историю, правила подключаются извне без внедрения файлов. Проверяй refs и LFS. Публичная копия приватного проекта имеет разрешённый состав и проверку истории/артефактов. Шаблон проверяется созданием проекта. Архив явно сообщает статус и учитывается без реактивации.

## REPO-012 Релизы и сопровождение

MUST | repository | pr-and-release

Релиз содержит версию, commit, артефакты, суммы и описание изменений RU/EN. Выпущенные версии не перезаписываются; stable, preview и rolling различимы. Скачивание, установка и обновление проверяются как пользователем. Сохраняй лицензии, SECURITY и поддержку. Следи за зависимостями и эксплуатируемыми уязвимостями; формируй SBOM/provenance при поддержке. Опиши экспорт и удаление данных.

## REPO-013 Явные исключения

MUST | repository | pr-and-release

Исключение содержит правило, область, причину, риск, владельца, компенсацию и срок пересмотра. Запрещены широкое подавление сканирования и скрытое ослабление правил. Срочная правка остаётся небольшой; сокращение проверок требует явного записанного решения и последующего закрытия. Изменения защиты ветки, прав и docs-policy видны отдельно.

## REPO-014 Приватный профиль исполнения

MUST | repository | pr-and-release

Пути рабочей станции, внутренние адреса, доступы, правила допуска к общим ресурсам и бюджеты исполнителей находятся в приватном профиле владельца. Публичные команды переносимы. Сохраняй границы полномочий и чужие задания. Приватный журнал эксплуатации не включается в распространяемый пакет.

## REPO-015 Проверенное подключение

MUST | repository | pr-and-release

Учитывай применимость и доказательства. Проверь чистый bootstrap, отклонение синтетического секрета, неверное форматирование, отсутствие/удаление языковой пары, фиктивные docs-правки и недоступный инструмент. После merge проверь защиту хостинга, затем установку и профильную приёмку. Распространяй версионированный пакет с суммами без приватного реестра. Зелёный общий CI не удостоверяет весь продукт.

# Профили продуктов

## web Браузер и PWA

Основные сценарии, offline/error/loading, доступность, мобильная вёрстка, кеш и обновление.

## mobile Android и Wear

Подписанное обновление без потери данных, целевое устройство, отказ разрешений, фон, перезагрузка, часовой пояс и синхронизация телефона/часов.

## cli CLI и desktop

Чистая установка, поддерживаемые ОС/shell, Unicode и пробелы в путях, exit code, отмена и миграция конфигурации.

## library Библиотеки и API

Минимальный пример потребителя, совместимость контрактов/версий, семантика ошибок и поддерживаемые runtime.

## service Сервисы контейнеры и MCP

Минимальные права, запрещённые операции, отзыв, readiness/liveness, restart, ограниченные очереди и идентичность исходников/артефакта/runtime.

## network Сети и VPN

Потеря контроллера/канала, устаревшая телеметрия, переключение и возврат, границы DNS/IPv6, восстановление доступа, задержка под нагрузкой.

## integration Интеграции и темы

Заявленные версии upstream, вход/управление, светлая/тёмная тема, длинные локализованные строки, клавиатура и целевая платформа.

## infra Инфраструктура и GitOps

Явная цель/контекст, безопасный plan/diff, ограниченное применение, readback, дрейф, откат и идемпотентность фактического повторного применения.

## monitoring Мониторинг и exporters

Нет/устаревшие данные отличаются от нуля, сброс счётчика, ограниченная cardinality меток, права агентов и полный путь алерта.

## data Данные медиа и backup

Сохранение источника, устойчивые задания, повреждённый ввод, дубли, пауза/продолжение, полный диск, семантический restore в изоляции и retention.

## ml ML и речь

Лицензии моделей/данных, фиксированный набор качества, тишина/шум, сравнение версий модели, RAM/VRAM/стоимость, CPU fallback и отмена.

## firmware Прошивки и устройства

Точная ревизия устройства, ограничения воздействий, стоп/обрыв, отсутствие самозапуска, восстановление и проверка физического результата.

## docs Документация и шаблоны

Рабочие внутренние ссылки, языковые пары, корректные команды/примеры и успешное создание проекта из шаблона.
